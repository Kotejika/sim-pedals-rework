# Аудит исходников V2 и решение по архитектуре

Дата: 2026-11-11

## Вывод

**V2 достаточно хороша как инженерная основа. Полный rewrite прямо сейчас не нужен.** Оставляем структуру V2 и делаем адресные исправления, а не переписываем рабочие подсистемы ради переписывания.

Это не означает, что V2 готова к прошивке: README автора прямо говорит, что сборка и host-тесты были сделаны, но на реальном железе проект не проверялся. Релизной или аппаратно-валидированной её считать нельзя.

## Что в V2 уже сделано правильно

- Радиоканал — Nordic Enhanced ShockBurst (ESB), а не BLE. Режимы PTX на узле педалей и PRX на Hub, 2 Mbps, 16-bit CRC, auto-ACK/retry. Протокол вынесен в общий `common/pedal_protocol.h`.
- ADS1220 выделен в отдельный драйвер; конфигурация рассчитана на дифференциальный AIN0-AIN1, gain 128, continuous conversion, 1000 SPS и AVDD как reference (ratiometric bridge).
- SS49E газа/сцепления читаются через SAADC, настройки каналов находятся в overlay.
- Hub делает общий pipeline осей: фильтрация, калибровка, инверсия, deadzone, response curve; математика вынесена в `common/axis_proc.c`.
- Есть C-тесты и Python mirror/golden-vectors: локально пройдены 27 golden rows и C axis tests.
- USB HID joystick отделён от vendor HID интерфейса конфигурации. Это хорошая основа для совместимости с играми и отдельного приложения.
- В проекте один протокол для радио и один для PC-конфигурации; это лучше, чем смешивать транспорт, фильтрацию и UI в одном модуле.

## Конкретные проблемы и риски, которые нужно исправлять/проверять

### P0 — подтверждать до аппаратной прошивки

1. **Питание внешней сенсорной шины P0.13.** В `firmware_pedals/Kconfig` по умолчанию включён active-high. Сам README V2 признаёт, что полярность не проверена. Нельзя менять этот флаг наугад: нужно сверить схему конкретной платы/ключа и проверить напряжение на шине при boot, active и sleep. Тот факт, что 3.3 V присутствуют на ADS DVDD/AVDD, не доказывает корректность P0.13 для отдельной rail-схемы.
2. **ADS1220 driver error handling недостаточен.** В `ads1220_init()` коды возврата RESET/WRITE/READ SPI операций не проверяются отдельно; проверяются только значения регистров 0..2 (не все четыре). Нужно проверять каждую SPI/GPIO операцию, читать back все четыре регистра, считать DRDY edge/timeout и вести конкретный fault code.
3. **Таймаут DRDY — 5 мс при целевых 1000 SPS.** Один пропуск/долгая задержка сразу обнуляет brake и переводит ADS в fault; повторная попытка init идёт раз в секунду. Это чрезмерно грубая диагностика: кратковременная задержка планировщика и реальный отказ датчика не различаются. Исправлять надо конечным автоматом с несколькими пропусками подряд, счётчиками и повторной синхронизацией, сохранив fail-safe (не выдавать последнее значение бесконечно).
4. **1000 Гц пока только настройка/цель, а не доказанная частота end-to-end.** Main loop ждёт DRDY, затем синхронно читает два Hall ADC канала с oversampling=16 и отправляет ESB payload. В реальности sample→radio частота зависит от времени этих операций, планировщика и ESB FIFO/retry. Нужны sequence-gap counters, timestamp/latency/jitter instrumentation и измерение на Hub. Нельзя обещать 1 kHz только по 1000 SPS ADS.
5. **Hub PRX ACK-payload очередь.** `queue_ack()` вызывается из `on_data()` после получения текущего пакета. В ESB PRX ACK payload назначается для следующего успешно принятого пакета, а не задним числом к уже принятому. Это может добавлять один пакет задержки командам Hub→pedals. Кроме того, `ESB_EVENT_TX_SUCCESS` сбрасывает `ack_queued[]` сразу для всех pipes, а аварийный `esb_flush_tx()` тоже глобальный. Для одного pedal-node это может работать, но multi-pipe/state handling хрупкий. Нужно привести очередь к documented ESB event ordering и отдельно тестировать доставку команд; auto-ACK самого data packet — отдельный механизм, не путать его с ACK payload команды.
6. **Failsafe должен различать stale link и sensor fault.** Hub сейчас обнуляет все оси, когда последний radio packet старше 50 мс. Sensor fault передаётся отдельным flag, это правильно. Нужно сохранить раздельную диагностику и не скрывать потерю последовательности пакетов.
7. **Проверить плату/overlay физически.** Overlay заявляет pin map Pro Micro/nice!nano: ADS D2..D6, Hall A0/A1, P0.13 rail. V4 UF2 strings подтверждают NCS 3.1.1 / Zephyr 4.1.99, как и V2 README, но не раскрывают конфигурацию V4 и не доказывают точный board revision.

### P1 — качество и диагностика

- Hub radio code считает пакеты за секунду, но пока нет per-device sequence gap/loss/duplicate stats и timestamp delta distribution.
- Текущий PC V4 app ожидает счётчики в хвосте live HID report (bytes 52..63): `rx_ok, tx_ok, rx_bad, bad_len, bad_b0`. V2 `usb_cfg_enqueue_live()` заполняет только device records и не записывает эти counters. Если оставить V2 Hub, нужно добавить согласованный versioned stats tail или изменить app parser с учётом версии протокола.
- В PC app reader thread завершает чтение после исключения из `dev.read()`; нужно добавить явный disconnected state/reopen backoff, не оставляя приложение с умершим reader.
- Запись settings во flash и авто-save надо проверить на влияния на radio/USB scheduling; сохранять не во время активного режима и коалесцировать записи.

## Что говорят локальные тесты

Запуск исходников V2 2026-11-11:
- `python3 -I tests/test_python_mirror.py` — OK, 27 golden rows.
- C axis tests с AddressSanitizer + UndefinedBehaviorSanitizer — OK.
- `python3 -m compileall -q pc_app` — OK.

Эти тесты проверяют математику осей/синтаксис PC-приложения, **не** проверяют ADS1220, ESB, USB enumeration или реальное время на плате.

## Решение

1. **Оставить V2 архитектурным baseline.** Не делать полный rewrite.
2. Перенести чистые V2 firmware/common/PC-app sources в репозиторий как отдельный baseline commit. Не переносить prebuilt V2 UF2 в папку релизов и не считать их эталоном.
3. В отдельной ветке делать маленькие измеримые изменения: сначала улучшенная диагностика ADS1220 + rail validation; затем ESB ACK command sequencing/loss counters; затем USB HID/app telemetry alignment.
4. После каждой правки — host tests + NCS 3.1.1 build обоих targets. После успешной сборки — hardware bring-up на обеих платах, сначала без нагрузки, потом с тензомостом.
5. Не прошивать новую версию, пока не проверены pin map/rail polarity и не сохранены исходные V4 UF2 для rollback.

**Итог:** V2 — нормальный фундамент, а не мусор. Главные недостатки — непроверенное железо, слабая диагностика ADS1220 и хрупкое управление ACK payload. Их можно исправить точечно, сохранив полезные части V2.
